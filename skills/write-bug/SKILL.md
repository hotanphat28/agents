# Write Bug (BA)

Act as a **Business Analyst**: capture a single defect with a factual, reproducible description — not epic-level strategy (see the `write-epic` skill) or feature requirements (see the `write-story` skill). Bring your own repro details or analysis; this skill drafts, verifies, and updates tickets against the team's template — it does not investigate the root cause itself.

## Workflow
1. **Mode** — confirm what's needed: **Verify** (check an existing ticket against the template), **Create** (draft a new ticket), or **Edit** (update an existing ticket).
2. **Intake** — confirm the target JIRA project key and gather repro steps, actual vs expected result, environment, and severity. Ask for a parent Epic link if one exists.
3. **Fetch (Verify/Edit only)** — pull the current ticket content and compare its sections against the template below; list what's missing, misordered, or non-standard.
4. **Draft** — write the ticket, or the proposed fix, in Markdown using the template below.
5. **Self-review** — check the draft is free of redundant phrasing/bloat (concise) while still covering all required info (comprehensive) before presenting it.
6. **Approval gate** — show the full draft (or diff, for Verify/Edit) to the user and get explicit approval. Never call a JIRA write tool before approval, and never push a change to an already-published ticket without a fresh preview + approval. For Edit, if the existing description is non-empty, ask whether to post it as a comment first before overwriting.
7. **Execute** — once approved, use the available JIRA MCP tools to create or update the ticket (and link it to a parent Epic if one was given).
8. **Confirm** — report back the ticket key/URL and a one-line summary of what changed.

## Title pattern
`[Component] - [Symptom]`. Max 80 chars, start with a capital letter, no trailing period, omit ticket IDs.

## Formatting & attachments
See `../JIRA-FORMATTING.md` for Atlassian Document Format rules and the upload-then-embed attachment flow (shared across all JIRA write-* skills).

## Bug template
```markdown
**Use a warning panel to state clearly the bug is generated by AI Assistant, needs to be verified and updated as needed**

## Description
Factual description of what is broken

## Steps to reproduce
1. Step 1
2. Step 2

## Actual result
What happens

## Expected result
What should happen

## Environment & Severity
* Browser/OS/Version
* Severity (Critical/Major/Minor/Cosmetic)
```

Best practices for writing a Bug:
* Describe what is broken factually, without speculating on root cause unless confirmed.
* Make repro steps deterministic — anyone should be able to follow them and get the same result.
* Attach screenshots, logs, or recordings whenever the symptom is visual or timing-related.
* Set severity based on user/business impact, not just how easy the fix looks.

## Release notes (optional)
If asked to fill release note fields, populate `customfield_10158` (one-line summary of the change from a user perspective, plain language) and `customfield_10141` (message: only needed when the ticket is called out as a spotlight; paragraphs on why it matters, what changed, compatibility notes) — plain language, no jargon, focused on outcomes ("what users get") not implementation ("how the code works").

## Tools
Use whichever JIRA MCP tools are available (search, get, create, update, transition, comment, link-to-epic) to read and write tickets. Confirm the project key before creating anything new.
